# 面试题库 100 题 · 参考答案（二）：推理篇 + 部署工程篇 + 项目开放题

## 推理篇（61–84）

**61.** temperature：logits/T 再 softmax，T<1 更尖、T>1 更平；top-k：只保留概率前 k 个候选；top-p：保留累积概率达 p 的最小集合（候选数自适应）。数学/代码/信息抽取 → 贪心或低温；对话/创作 → 适度高温 + top-p≈0.9。

**62.** 权重 ≈ 2 GB（FP16，2 字节/参数）+ KV cache（随上下文）+ 激活与框架开销 1~2 GB → 实际约 2.5~3 GB 起。

**63.** TTFT：首 token 延迟（主要由 prefill 决定，与 prompt 长度和排队有关）；TPOT：每 token 生成延迟（由 decode 决定）；吞吐：系统每秒输出 token 数（batch 与调度决定）。

**64.** 无 cache 则每步都要重算全部历史的 K/V，计算随生成步数二次恶化、显存读写爆炸。cache 用空间换时间，是自回归推理可行的基础。

**65.** decode 是 memory-bound：每步读入全部权重只算一个 token，batch 增大等于把一次权重读取摊给多个请求 → 吞吐近线性提升。上限：KV cache 挤爆显存、或算力打满后转为 compute-bound，边际收益消失。

**66.** 参数量 × 每参数字节数：FP16=2B、INT8=1B、INT4=0.5B；再加 KV cache 和 1~2 GB 运行时开销。例：7B FP16 ≈ 14 GB，INT4 ≈ 3.5 GB。

**67.** 2 × 24 层 × 8 kv_heads × 128 head_dim × 8192 seq × 8 batch × 2 bytes ≈ **6.4 GB**。顺序：2(K,V) × 24 × 8 × 128 × 8192 × 8 = 3.2×10⁹ 个元素 × 2B。要点是先写公式再代数。

**68.** 问题：KV cache 传统按 max_len 预留连续显存 → 内部碎片 + 外部碎片，并发上不去。机制：借鉴 OS 虚存，把 KV cache 切成固定大小 block 按需分配，用 block table（逻辑块→物理块）管理 → 显存利用率大幅提升，同显存容纳更多并发，还支持块共享。

**69.** 静态 batching：凑一批等到最长序列完成才能进新请求，短序列空转等长尾；continuous batching：每次迭代（甚至每步）动态插入新请求、移除完成请求，GPU 常满载 → 吞吐数倍提升。

**70.** 相同前缀（系统提示、few-shot、多轮历史的公共部分）的 KV 只算一次，物理 block 被多请求共享（引用计数）→ 省 prefill 计算与显存。适用：固定系统提示、RAG 多问题同文档、高重复前缀的业务。

**71.** prefill：整个 prompt 并行算，compute-bound → 优化算子/FlashAttention/并行；decode：一次出 1 token 却读全部权重，memory-bound → 优化 batching、KV cache（GQA/量化/分页）、投机解码。

**72.** 标准 attention 要把 n×n 矩阵写入 HBM（显存 O(n²)、读写巨量）；FlashAttention 用 tiling 分块 + online softmax 在 SRAM 内算完，不物化注意力矩阵 → 显存 O(n)，快在减少 HBM 读写。复杂度仍是 O(n²)，没降。

**73.** AWQ（激活感知量化）：统计激活分布，对高激活通道的权重做 per-channel 缩放保护后再量化；不需重训、对校准数据依赖小。GPTQ：基于二阶（Hessian）信息的逐列量化 + 误差补偿到未量化列。GPTQ 压缩-精度比好，AWQ 简单鲁棒，都是 4-bit 常客。

**74.** 流程：固定评测集对比 FP16 基线 → PPL 差异 + 通用 benchmark（MMLU 等）+ 业务集准确率 → 人工抽测 open-ended 生成。标准示例：任务准确率下降 <1%、PPL 涨幅可接受、无明显格式劣化才上线；灰度对比兜底。

**75.** 小草稿模型快速生成 k 个候选 → 大模型一次前向并行验证整段 → 按拒绝采样规则接受/修正。拒绝采样保证最终输出分布与大模型自回归采样完全一致 → 无损。

**76.** Megatron 式 TP：每层两次 all-reduce——attention 输出投影后一次、MLP 下投影后一次；n 层共 2n 次。通信在关键路径上，所以 TP 限制在 NVLink 机内、跨机用 PP。

**77.** 把长 prompt 的 prefill 切成多块，与 decode 迭代混合调度。解决：超长 prompt 独占 GPU 导致其他请求排队（TTFT 飙升）的问题，平衡 prefill 与 decode 的资源占用。

**78.** gpu_memory_utilization：预留给模型+KV 的显存比例（留余量防 OOM）；max_model_len：限制最长序列（直接决定 KV cache 上限）；max_num_seqs：单批最大并发。调法：先保守基线 → 压测看 KV 占用与排队 → 逐项放开逼近显存上限 → 以 P99 达标为准。

**79.** block table 记录每个序列的逻辑块→物理块映射；相同前缀指向同一物理块（引用计数>1）；当共享块需要被追加/修改（如分支采样、beam search 分叉）时 copy-on-write：复制出私有块再写。能讲清"共享+写时复制"就到位。

**80.** 加速比 ≈ 1 / (1 − α(1 − 1/c))，α 为平均接受率（接受 token 占比）、c 为草稿与目标模型的单步成本比。α→1 且 c 大时接近 c 倍；实践中草稿便宜 5~10 倍、接受率 70%+ 时常见 2~3 倍加速。要点：说出"接受率越高、草稿越便宜加速越大"和公式形态。

**81.** 现象：LLM 激活存在极少数巨大 outlier 通道 → per-tensor 的 scale 被极端值拉大，其余权重全部压到量化台阶内失真。SmoothQuant：按通道算缩放 s_j = max|X_j|^α / max|W_j|^(1−α)，把激活的量化难度按比例"搬"到权重上（s 同时除激活、乘权重），实现 W8A8 稳定量化。

**82.** prefill（compute-bound、突发、短）与 decode（memory-bound、持续、长）资源画像相反，混部互相干扰、扩容只能整体扩。分离后各自独立扩容与调参，TTFT 和 TPOT 双优化（DistServe/Mooncake 等）。最大挑战：分离实例间的 KV cache 传输（要 RDMA 级互联）+ 全局调度一致性。

**83.** FP8 两种格式：E4M3（精度高、范围小）常用于前向权重/激活，E5M2（范围大）用于反向梯度。范围远小于 FP16 → 必须 per-tensor/per-block scaling；主流按 128 元素 block 校准，平衡精度与开销。

**84.** 经典投机解码：独立小模型出草稿、大模型验证。Medusa：目标模型自己加多个解码头，一次并行预测未来多个位置，配树注意力验证——不用额外小模型。EAGLE：在特征层（倒数第二层隐状态）做自回归草稿，利用更多信息、接受率更高。共同点：都是"草稿+验证"框架下的变体。

## 部署与工程篇（85–94）

**85.** 清单：①加载校验（权重/config/tokenizer 版本）②参数基线（max_model_len、max_num_seqs、gpu_memory_utilization 按显存算）③warmup 预热（防首请求超时）④压测基线（并发梯度下的 TTFT/TPOT/吞吐）⑤精度验证（与参考实现对齐）⑥监控告警 + 回滚预案。

**86.** 指标：GPU 利用率/显存、队列长度、TTFT/TPOT/吞吐 P99、抢占（preemption）次数、cache 命中率。判瓶颈：GPU 打满但吞吐不再涨 → 调度/参数或 compute 瓶颈；GPU 空闲但队列长 → 上游并发/部署实例不足。

**87.** 判断依据：单卡显存放不放得下 + 延迟要求 + 成本。放得下且并发高 → 多实例（横向扩、故障隔离、简单）；放不下或单请求延迟要求高（大模型长上下文）→ TP 切分（通信有代价，延迟未必线性降）。

**88.** 预热：启动后立即跑 dummy 请求编译/建 cache；加载：pinned memory、多流并行读盘、权重直接从共享存储流式加载；热切换：多进程实例池 + 负载均衡摘挂、vLLM sleep mode 释放/唤醒权重。

**89.** SSE/HTTP chunked 逐 token 下发。首 token 延迟 = 排队时间 + prefill 时间（与 prompt 长度成正比）+ 调度间隙。缩短手段：prefix caching 免重复 prefill、chunked prefill 防长 prompt 阻塞、优先级调度。

**90.** FLAT：精确暴力、小数据；IVF：聚类倒排，nprobe 控制召回-速度，内存省；HNSW：图索引，高召回低延迟但内存大、建图慢。选型口径：小规模要精确 → FLAT；大规模内存敏感 → IVF(+PQ)；低延迟高召回 → HNSW。

**91.** HNSW：多层"跳表式"近邻图，查询从顶层贪心下行。M（每节点连接数）越大召回越高、内存越大；ef（搜索时候选队列）越大召回越高、延迟越高。调参本质是召回率-延迟-内存三角的权衡，用业务评测集（recall@k）定。

**92.** chunking：按语义边界（标题/段落）切 + 适度 overlap，避免切断答案所在句；rerank：粗召回 top-20~50 后用 cross-encoder 精排到 top-3~5。评估：检索层看 recall@k / MRR，端到端看答案准确率，两层分开归因。

**93.** 体系化答案框架：①模型层——换更小模型/蒸馏/量化（W4A16）验证效果不掉；②调度层——prefix caching、continuous batching 参数、max_num_seqs 逼近显存；③系统层——PD 分离、autoscaling 砍闲时实例、spot 实例；④业务层——缓存高频问答、截断无效长 prompt。强调：每一刀都要有压测数据支撑。

**94.** 考察方法论，用 STAR：现象（监控怎么发现）→ 定位路径（从指标分层排除：GPU/调度/网络/上游）→ 根因（具体到机制）→ 修复（参数/代码/架构）→ 预防（加监控/压测用例/文档）。提前准备一个真实案例，讲得出细节才有说服力。

## 项目与开放题（95–100）

**95.** 模板：背景（业务问题 + 为什么需要微调）→ 任务（base 模型、数据规模、SFT+DPO）→ 动作（数据 pipeline、3 组对照实验、评估体系）→ 结果（量化指标 + badcase 下降 + 部署上线）。准备 2 分钟版和 5 分钟深挖版两个口径。

**96.** 展示决策链而非结论：任务难度与上下文长度 → 显存/算力预算 → 候选模型中文能力对比 → 选 0.5B~1.5B 是为了快速迭代可复现 → 主动承认局限（知识容量、复杂推理弱）+ 后续升级路径。

**97.** 来源（开源数据集/自建/业务脱敏合成）→ 清洗 pipeline（规则过滤、质量打分模型、去重：精确+模糊、长度分布、格式校验）→ 配比与难度分层 → 人工抽检标准与抽样率。突出你 YOLO 时代的数据经验迁移。

**98.** 三层：自动评测集（自建 30~50 条 + 通用 benchmark）→ 人工评分（多维 rubric：相关性/正确性/格式）→ 业务代理指标。归因靠消融：换数据/换超参/换方法逐项对比，"提升 X% 来自哪里"要答得出来。

**99.** 框架：数据 ×10 → 不只是堆量：扩领域覆盖、难度分层、上分布式清洗 pipeline、重新配比；算力 ×10 → 换更大 base 或全参微调、更长训练 + 系统性超参搜索、上分布式训练（ZeRO/TP）；不变项：仍然先小规模实验再放大（这是加分点）。

**100.** 叙事：CV 训练给了我完整的"数据→训练→评估→部署"方法论（过拟合直觉、数据质量敏感度、调参手感）；现在职做 LLM 部署补上了推理工程；差异化 = **能训（新项目）+ 能部署（在职）+ 懂原理（本题库）** 的全链路工程师，且已在真实生产环境跑 LLM 服务。避免说"CV 不行了才转"。
